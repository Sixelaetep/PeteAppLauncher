Full version history for `film-tv-tracker.html`. As of v1.2, new entries go here in full; the inline comment in the `.html` gets a short pointer only, to avoid the file bloating.

## v1.6 (FTT-009) — Dashboard stat boxes are clickable

Pete's direct request, from a screenshot of the dashboard's stat row. Each of the six boxes now jumps to the tab/filter that produced its number:

- Want to Watch → Watchlist, filter "All"
- Watched → Watched, filter "All"
- Available Now → Watchlist, filter "Available to me"
- Unavailable → Watchlist, filter "Unavailable"
- Services owned → Services tab
- Favourites → Watchlist, filter "Favourites"

New `goToStat(tab, filterElId, filterValue)` calls `switchTab()` then sets the named filter `<select>`'s value and re-renders just that one panel, so the filter takes effect immediately rather than waiting for the next interaction. `.stat-box` got a pointer cursor and a hover border to make them read as clickable.

**Favourites is worth flagging rather than leaving quietly inconsistent:** the stat itself counts every favourited title regardless of status (watched or watchlist), but there's no single view that shows both together — clicking it goes to the Watchlist tab's own Favourites filter (matching the "Favourite Watchlist" dashboard section directly below it), which only shows watchlist favourites. A favourited *watched* title has its own Favourites filter on the Watched tab, just not reachable from this one click. Flagged rather than fixed unasked — a combined "all favourites regardless of status" view is a reasonable follow-up if it'd be more useful than the current per-tab split.

Tested: `node --check` on both script blocks, a full id cross-reference, an HTML tag-balance check. Not tested live in a browser.

## v1.5 (FTT-008) — Generic JSON import for viewing history and watchlist

Pete's direct request: a JSON-based import (he doesn't have the source file yet, but wanted the mechanism ready) for two separate cases — viewing history (mark watched) and watchlist (want to watch) — reusing the CSV importer's matching/dedupe machinery rather than a parallel implementation.

**Schema, deliberately lenient** since the exact source isn't known yet: accepts a bare JSON array, or `{"titles": [...]}`; each entry can be a plain string or `{"title":"…","year":2020,"type":"movie"}` (`year`/`type` both optional — a year disambiguates a common title, a type skips guessing film vs TV and searches TMDB's typed `/search/movie` or `/search/tv` endpoint directly instead of `/search/multi`). Verified standalone under Node against all three shapes (bare array, wrapper object, and malformed/empty input) before wiring it into the app.

**Dedupe rules, per Pete's spec exactly:**
- *Viewing history import:* a title already in the library that isn't yet watched gets flipped to watched; one already watched is a true duplicate and is skipped (counted, not silently lost); a title with no existing match gets a full TMDB details fetch and is added as watched.
- *Watchlist import:* a title already in the library in **any** status is left alone — never downgrades something already watched back to watchlist, and never duplicates something already on the watchlist. Only genuinely new titles get added, as watchlist.
- Either way, matching happens by TMDB id after resolving the search (not raw text), so "Dune" vs "Dune (2021)"-style spelling differences don't create false non-duplicates. Anything TMDB can't match at all is still added — flagged in its notes for manual review, same convention as the CSV importer — rather than dropped.

**Refactor, not a third copy-pasted importer:** the Netflix CSV importer's progress/cancel UI (`netflixImportControls`/`Running`/`Progress` ids) was renamed to the generic `importControls`/`importRunning`/`importProgress` and is now shared by all three import buttons — only one can run at a time regardless, so one progress area is simpler than three near-identical ones. `cancelNetflixImport()`/`_netflixImportCancel` were renamed to `cancelImport()`/`_bulkImportCancel` for the same reason. `importNetflixCSV()`'s own logic is untouched beyond the id/name updates.

Tested: `node --check` on both script blocks, a full id cross-reference, an HTML tag-balance check, and the JSON parser run standalone against all three documented input shapes plus two error cases — all pass. Not tested live: the actual TMDB matching (same standing limitation as the CSV importer — no network path to api.themoviedb.org from the build sandbox), and there's no real source file yet to try an end-to-end import against.

## v1.4 (FTT-007) — Season progress denominator fix, every season shown

Pete asked directly whether "6/9 seasons watched" was actually implemented, which surfaced a real gap: `seasonsWatchedSummary()`'s denominator was `Object.keys(t.seasonsProgress).length` — the count of seasons that had ever been *touched* (loaded or marked) — not the show's actual total season count. A 9-season show with only 6 seasons ever marked would have shown "6/6" (100%), not "6/9". Fixed to use `t.seasons` (the real total, already known from TMDB) as the denominator, falling back to the touched-count only for a title with no known season total at all.

`renderSeasonsList()` had the same shape of gap the other way round: it only rendered rows for seasons already in `seasonsProgress`, so an untouched season 7, 8 or 9 wouldn't appear at all — no way to mark it watched without first using "Load / refresh season data" for the whole show. It now always lists every season 1..`t.seasons`, rendering a plain "Season N — not started" row with a one-click "Mark watched" for anything not yet touched, alongside the existing per-episode checklist for seasons that have full data and the "imported/marked, no episode detail" summary for lightweight ones. Added `quickMarkSeasonWatched()`/`unmarkSeasonWatched()` (the latter — an explicit "Unmark" button — didn't exist before this release at all, for any season).

Tested: the fixed `seasonsWatchedSummary()` logic was run standalone against a mock 9-season title with 6 seasons manually marked — confirmed it now returns `{fully: 6, total: 9}`. `node --check` on both script blocks, a full id cross-reference, and an HTML tag-balance check all pass. Not tested live in a browser.

## v1.3 (FTT-006) — Netflix history import, "times watched"

Pete uploaded a real Netflix "Viewing history" CSV export (`NetflixViewingHistory.csv`, ~3,060 rows) and asked for it to populate historical watched data: no duplicates (a count instead, for rewatches), and season-level rather than episode-level marking for TV.

**Parsing.** Netflix's export has no structure beyond `Title,Date` — a proper quoted-CSV parser was needed (some titles contain commas, e.g. "Subways, Bicycles and Automobiles"). The `Title` column itself conflates show name, season, and episode with no consistent delimiter: verified against Pete's actual file that splitting each title on `": "` and looking for a `Season N` / `Series N` / `Limited Series` / `Miniseries` segment cleanly resolves 166 shows across 277 distinct (show, season) pairs — that part is unambiguous. The remaining 1,060 distinct strings have no season marker at all, and are a genuine mix of real films (`Freefall: A Reckoning for Boeing`) and anthology/documentary-series episodes with no season label in the export (`Mating Season: The Wolf Wedding`, `Untold Mr. T: I Pity The Fool`) — text alone can't reliably tell these apart.

**Matching heuristic (imperfect, documented rather than papered over).** For the 166 explicit shows: search TMDB for the show name, require a `media_type: 'tv'` result, done. For the 1,060 ambiguous strings: first try the text before the first `": "` as a candidate show name, but only accept it if TMDB's top result is a TV show whose name matches that candidate *exactly* (case/punctuation-insensitive) — this correctly catches "Mating Season" and similar. If that fails, fall back to searching the *entire* raw string and accepting whatever TMDB returns (film or TV), which is why a docuseries with a colon in its own official name (`Turning Point: Generation 9/11`) still resolves correctly even though the naive first-colon split would have broken its name in half. Anything with no TMDB match at all is still added — as a plain watched title using the CSV's exact text, flagged in its notes for manual review — rather than silently dropped.

**No duplicates.** Every resolved show/film is checked against the existing library by TMDB id before creating anything: a show already in the library gets its new seasons merged in (not a second Title record); a film already in the library gets `timesWatched` incremented instead of a duplicate entry. A season is recorded via a new lightweight `seasonsProgress[n] = { manuallyMarkedWatched: true, episodeList: [], … }` shape — deliberately *not* fetching each season's real episode list during import (that would be another TMDB call per season per show, and Pete explicitly didn't want episode-level import). `seasonsWatchedSummary()` and the modal's season list both treat `manuallyMarkedWatched` as "fully watched"; if the title's own "Load / refresh season data" is used later, real episode data is merged in and — specifically for a season that was only ever whole-season-marked — every episode in it is promoted to watched rather than the season appearing freshly empty.

**New `timesWatched` field.** Added to the Title record and a "Times watched" input in the modal's watched-fields section (editable like anything else); watched cards now show "Watched ×N" in their meta line when N > 1.

**Scale and safety.** ~1,226 unique shows/films to resolve, up to 2 TMDB searches + 1 details call each — a deliberate one-request-at-a-time loop (150ms spacing, not because of a documented TMDB rate limit, just politeness) means a history this size takes several minutes; the Data Modal shows a live added/merged/unmatched count and a Cancel button. Local storage is saved after every processed row (so a cancelled or interrupted run keeps everything done so far); cloud sync is one bulk push of everything touched, at the end or on cancel, not interleaved per-row.

Tested: the deterministic parsing/grouping half (CSV parser + the show/season-marker split) was ported into a standalone Node script and run directly against Pete's actual uploaded file — confirmed 166 shows / 277 (show, season) pairs / 1,060 atomic strings, matching an independent Python analysis of the same file exactly. `node --check` on both inline script blocks, a full id cross-reference, and an HTML tag-balance check all pass. Not tested, and impossible to test from the build sandbox (no network route to api.themoviedb.org): the live TMDB matching itself — the exact-name heuristic, the fallback full-string search, and how well real search results behave across all ~1,226 unique entries. Recommend a first run on the real file and a skim of the Data Modal's final added/merged/unmatched counts before assuming it's clean; the unmatched bucket and any obviously-wrong merges are easiest to spot and fix right after that first run.

## v1.2 (FTT-003, FTT-004, FTT-005) — Sync-chip parity, search add-as-watched, multi-select, episode tracking

Four changes, all Pete's direct request in one message.

**(1) Sync-chip parity (FTT-003).** Replaced the plain sync-dot + two collapsed Settings/Backup `<details>` panels with the suite-standard sync-chip + Data Modal, matching Fortnight Tracker v3.71 (and On Budget / Claim Tracker / Test & Issues) exactly: a tinted pill in the header (`state-local` / `state-connecting` / `state-syncing` / `state-synced` / `state-error`) that opens one modal containing a library summary, cloud sync status + Pull/Push buttons, a sync log, this app's own Preferences (bedtime threshold), storage info, and JSON backup/restore — one entry point instead of three separate UI elements. Added `slog()`/`renderSyncLog()`, `setSyncStatus()` (now folds in `window.PalSync.retryQueueLength()` the same way Fortnight Tracker does, showing "N pending sync" over a bare error while a retry is queued), `manualPull()`/`manualPush()`, and a `no-pal-banner` shown when no `PAL_SESSION` arrives within 3s. `state.lastUpdated`/`state.lastExported` are now tracked for the Storage panel. No data-model changes — purely a UI/sync-status rewrite.

**(2) Search: add to Watchlist or Watched (FTT-004a).** Each search result now has two actions — "+ Watchlist" and "✅ Add as Watched" — instead of a single "+ Add". `tmdbToTitle()` takes a `status` parameter; adding as Watched stamps `watched.date` to today with no rating/review (editable immediately after, same as any other watched title).

**(3) Watchlist multi-select + quick actions (FTT-004b).** A "☑ Select" toggle on the Watchlist tab switches cards into a selectable state (checkmark overlay instead of opening the modal on tap) with a bulk-action bar — Favourite, Mark Watched, Remove — for whatever's selected. Outside select mode, Watchlist cards also gained a quick "✅ mark watched" button alongside the existing quick-favourite star, so both don't require opening the modal. `titleCardHtml()` now takes an `opts` argument (`{selectable, showQuickWatched}`) rather than being watchlist/dashboard/watched-specific — dashboard and Watched cards render exactly as before (no `opts` passed, same click-to-open + fav-star behaviour).

**(4) Episode-level tracking (FTT-005).** A TV title's modal now has an "Episodes & Seasons" section: "Load / refresh season data" fetches every season 1..N from TMDB (`/tv/{id}/season/{n}`, one call per season, only when the user opens this — not forced on every TV title), rendered as collapsible per-season blocks with a checkbox per episode and a "Mark all watched" quick action per season. Progress (`t.seasonsProgress[season] = {episodeCount, name, episodeList, watchedEpisodes}`) is stored on the Title itself and syncs like any other title field — no separate table. Cards and the modal summary now show "N/M seasons watched" (via `seasonsWatchedSummary()`) once season data has been loaded, in place of the plain seasons count. Episode/season ticks save and sync immediately (not gated behind the modal's own Save button), consistent with how favourite/quick-watched already behave. Deliberate v1 simplifications, flagged rather than silently assumed: TMDB's `number_of_seasons` excludes "Specials" (season 0), so specials aren't fetched; a title added manually (no TMDB match) shows a note that episode tracking needs a TMDB-matched title instead of silently doing nothing.

Tested: `node --check` on both inline script blocks after every change, a full id cross-reference (no missing/duplicate ids), and an HTML tag-balance check. Not tested live in a browser: the actual TMDB season-fetch response shape (no network path to api.themoviedb.org from the build sandbox), and Supabase sync of the larger `seasonsProgress` payload — both worth a first real check.

## v1.1 (FTT-002) — Modals were unclosable

`pal-shared.js`'s own `closeModal(id)` removes an `open` class — the convention Claim Tracker/Gym Tracker use (`.modal.open`). This app copied `test-issues.html`'s `.modal-overlay.hidden` convention instead (add/remove `hidden` on the overlay), so every call to the shared `closeModal()` throughout this file was a silent no-op: it was removing a class (`open`) the overlay never had, while the class that actually controls visibility (`hidden`) was never touched. That's the exact bug behind "stuck in the modal" — Cancel, the click-outside handler, and (this release's own addition) a new ✕ button were all correctly wired, but all three called a function that did nothing to this markup. Fixed by declaring this file's own `closeModal(id)` after `pal-shared.js` loads (function declarations in a later `<script>` win over an earlier same-named one on the same global) — every existing call site needed no changes. Also added: a visible ✕ close button on both modals (the backdrop-click target was only ~16px wide on a phone — real, but too easy to miss) and an Escape-key handler as a third way out on desktop.

## v1.0 (FTT-001) — New app

New personal catalogue/watchlist/review app for Pete's Apps. Dashboard, Watchlist, Watched, Services, Search/Add and Reviews tabs. TMDB (GB region) powers search, metadata, and watch-provider availability in one call per title via `append_to_response=watch/providers` — deliberately no second API in v1; Watchmode stays a candidate only if TMDB's provider coverage proves thin in practice. Availability is always kept separate from ownership: a title shows as available/unavailable/rent-buy against the user's own Services list, never hidden when unavailable, with the missing service named on the card. Bedtime mode is derived purely from episode runtime (show-level average for v1, not a manual tag) against a configurable 20/30/45-minute threshold. Cinema release date is stored for films with a "cinema UK" Google fallback rather than a guessed "currently showing" flag. Reviews live on the Title record and surface automatically once a title is marked watched. Data model, Supabase table (`pal_film_tracker`, `title_`/`service_` prefixes, single `__settings__` row) and sync all follow the established `pal-shared.js` `table()`/`pull()`/`upsert()` pattern. Manual entry remains fully supported; TMDB is enrichment, not a dependency for opening or browsing saved data.

`pal-shared.js` also updated alongside this release: added `TMDB_API_KEY`/`TMDB_READ_TOKEN` to `PAL_CONFIG`, same precedent as `FF_PROXY_KEY`.

Tested: `node --check` on both inline script blocks, HTML tag-balance check, full id cross-reference. Not tested: live TMDB calls or Supabase sync (both needed their first real run, done since).
