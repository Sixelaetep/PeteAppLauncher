# Film & TV Tracker — Changelog

Full version history for `film-tv-tracker.html`. As of v1.2, new entries go here in full; the inline comment in the `.html` gets a short pointer only, to avoid the file bloating.

## v2.2 (FTT-022) — My favourites: a personal shortcut shelf with manual ordering

A focused addition to the Library; the v2.1 design is otherwise unchanged. 109 functions are byte-identical to v2.1 (storage, all sync, backup/restore, the importers, the edit modal, detail, selection mode and `runBulk`). Eight existing functions changed and 17 were added; nothing was removed.

**The row.** **My favourites** now sits at the top of the Library content, above **Available to watch**, then **New seasons**, then the library. It reuses the same compact mini-card as the Available row (`miniCardHtml`, now with an options argument), so the rows look the same. Tiles show the poster and title only, plus the existing NEW / cinema indicators and a ✓ on watched titles; the ♥ is left off because every tile is a favourite. Favourites span both Want to Watch and Watched, so the row shows the same favourites in every status view. It follows the existing discovery rules: hidden when there are no favourites, hidden while searching, filtering or in selection mode. It shows the first 8 in saved order with **See all →** (only when there are more than 8), which opens the Favourites filter.

**Reorder — in two places, editing one order.** (1) On the home row, **Reorder** rearranges just the tiles shown (the top 8; it does not expand the row), with a hint that points to See all for the rest. (2) In the full list (the **Favourites** filter on its default or "My favourites first" sort) a **Reorder** control appears beside Sort and makes every favourite in the list draggable, with paging lifted so any one can be dragged anywhere. It is not offered under other filters or explicit sorts, where dragging wouldn't mean anything. Either way: drag with a mouse or finger (pointer events, one code path), or focus a tile and use ← / →; a drag starts only after 6px of movement and reorder tiles have no click handler, so it can never open a title. Nothing is written until **Done**; changing the view, leaving the Library tab, entering Select mode, or backgrounding the app while reordering also saves, so an unfinished reorder is never lost. Pressing the other Reorder control saves and switches. **One rule ties the two together:** whichever set you rearrange (the top 8, a filtered list such as Watched + Favourites, or everything) moves among the positions it already occupied, so every favourite you didn't touch keeps exactly its place. Move #12 to the front in the full list and it leads the home row; swap two watched favourites and nothing else moves. **The number of favourites is unlimited**: 8 is only how many tiles the home row displays, and the full list pages 60 at a time with Show more (tested with 70).

**How the order is stored.** A numeric `favouriteOrder` on each favourite title (1 = first). It is a per-title field on purpose: titles already sync record-by-record to Supabase and travel inside the JSON backup, so the order rides both with no new sync row and no change to the backup format. Only favourites carry it.
- *New favourite* (detail button, bulk Favourite, or the edit modal): appended to the end. Bulk favourite appends in the order you tapped the cards.
- *Un-favourite* (any route, including bulk Remove favourite): the number is removed, the title is untouched, and the other favourites' numbers are left alone. Re-favouriting appends it to the end again.
- *Reorder*: renumbers 1..n and saves/syncs only the titles whose number changed. Moving one tile to the far end changes every number in between, so that is up to n records pushed once, on Done. Each is an ordinary title update.
- *Upgrade / legacy data*: `ensureFavouriteOrder()` runs at boot and before every save. Favourites with no number (pre-v2.2 data, a pre-v2.2 backup, or a record arriving from an old client) are numbered **oldest-added first**, the same order new favourites are appended in. It also fixes duplicates and junk values (null, text, negative, fractional) by appending the offenders after those with valid unique numbers. The migration is silent: no `updatedAt` bump and nothing pushed to the cloud, so two devices with the same data derive the same numbers and there is no sync storm. It is written back to local storage once, at first open, so exports carry it from then on.

**Favourites filter and sort.** The filter chip is unchanged. Inside it, the list now follows the saved order by default (the Sort dropdown shows **My favourites first**), unless you have explicitly chosen another sort, which then wins. The old "Favourites first" sort is now "My favourites first": favourites in saved order, then everything else newest-first. Want to Watch + Favourites shows the same relative order.

Tested (headless Chromium; 390×844 touch, 820×1000 and 1280×800; a 438-title library whose four favourites carry no order, i.e. genuine legacy data; a stub `pal-shared.js` that records every upsert/tombstone): 85 feature checks plus the full v2.1 suite (76), zero JS errors, no horizontal overflow at any size including reorder mode. **Test-environment caveat:** when the page is loaded from a `file://` URL, headless Chromium intermittently discards a save across a page reload (the reloaded page starts from the original seed). That made the "survives reload" checks fail in roughly a third to a half of full runs, and it is not caused by v2.2: a plain "save, wait, reload" loop loses the save in 4/40 trials on the untouched v1.12, 3/40 on v2.1 and 2/40 on v2.2. Served over `http://` (the realistic case), v2.2 lost 0/40 of those trials and passed the full 85-check suite 6/6 runs. Not observed over http in 46 trials; a very low rate cannot be ruled out, so confirm once on a real device (reorder, Done, reload). A later addition (reorder on both the home row and the full list, and unlimited favourites) has its own 39 checks, also passing (run over `http://`), plus the earlier 85 and the v2.1 76 re-run against it. Feature checks cover: legacy migration (numbers, order, persisted, no `updatedAt` change); layout order and headings; row identical in every status; search hides it and clearing restores it; reload stability; append / remove / re-add through the detail button, the edit modal and bulk actions (order numbers and sync calls verified); 12 favourites with the 8-cap, See all and the filter/sort behaviour above; mouse drag forwards, to the very end, and backwards to the very start; a real CDP touch drag (ghost, reorder, no page scroll, no detail opened); Done persists to state, localStorage and reload with only the moved titles synced; keyboard reorder; commit on tab-switch and on entering Select mode; un-favouriting mid-reorder; export → wipe → import identical order; a pre-v2.2 backup; colliding order numbers; junk values; a favourite arriving from sync with no order.

Not tested: the real `pal-shared.js` and live Supabase (sync was exercised against a stub that records calls, so the merge of favouriteOrder between your phone and Lex's is reasoned about, not observed); a physical finger on a real iPhone (touch was synthesised through Chrome's input protocol, which drives the same pointer events but not iOS's own gesture handling); your real library; live TMDB; the launcher iframe. Note also that on a phone with all three rows populated, the "Want to Watch" library heading now starts near the bottom of the first screen — the price of putting favourites first, and the reason each row is capped.

## v2.1 (FTT-021) — Selection mode, delete from detail, dynamic heading, discovery/card polish

Targeted polish on v2.0; the Library design is unchanged. **No data-model change**: nothing renamed, added or removed, and 105 functions (storage, all sync, backup/restore, the three importers, the new-season check, service merge, the whole edit modal, `filterAndSort`, `resolveAvailability`) are byte-identical to v2.0. Only six rendering functions changed (`availabilityLine`, `renderLibrary`, `switchTab`, `titleCardHtml`, `toggleSelectMode`, `updateBulkBar`).

**Selection mode.** A small **Select** link sits beside Sort ("Sort: Recently added  Select"). Cards in normal mode have no checkboxes or buttons. In selection mode every card gets a checkbox, tapping a card selects it instead of opening detail, selected posters get a teal outline, and the discovery rows step aside. A compact bar is pinned to the bottom edge (thumb-reachable on a phone): `3 selected · Select all · Cancel`, then **Delete · Mark watched · Favourite** once something is selected. Cancel, Esc, switching to Services, or finishing any bulk action returns to normal browsing with the current status, filter and search untouched.

**Bulk-action framework.** Every action is one entry in `BULK_ACTIONS` (`label`, optional `show` / `prepare` / `confirm`, `apply`, `persist`, `done`) run by a single `runBulk(actionId, ids)`, which applies the change, stamps `updatedAt`, exits selection mode, calls `saveState()` and pushes each changed title to Supabase (upsert, or tombstone for deletes — the same calls v2.0 used). Adding "Mark unwatched", "Change service" and so on later means adding an entry, nothing else. The old `bulkFavourite` / `bulkWatched` / `bulkRemove` are gone, replaced by this. Contextual behaviour: **Favourite** becomes **Remove favourite** when everything selected is already a favourite; **Mark watched** is hidden when everything selected is already watched.

**Select all — what it covers.** Only the titles currently on screen in the filtered/searched view. The grid pages 60 at a time, so when a view has more than that the button reads "Select 60 shown" and a note says "Showing 60 of 108 — selecting covers the titles shown. Use Show more to include others." After Show more it selects the larger set. Related safety rule: if a filter or search change hides a selected title, it drops out of the selection, so "Delete N selected" can never include something you can't see.

**Delete.** Confirmation for one title: `Delete "Title" from your library?`; for several: `Delete 5 selected titles? They will be removed from your library.` (declining changes nothing and keeps you in selection mode). Non-destructive bulk actions have no confirmation. **Delete** now sits beside **Edit title** in the detail view and uses the same code path. Deletion is still a soft delete (`_deleted` + tombstone), exactly as before; there is no undo in the app.

**Heading.** Now reflects the primary state: *Want to Watch · 42*, *Watched · 87*, *All Titles · 129* (the number is the count for the current filter/search, and updates in place after a bulk action).

**Discovery rows.** Capped at 8 posters each; "See all →" appears only when there are more than 8. On a phone about four and a half posters show at once and the row scrolls, so the cap of 8 is what keeps it from growing.

**Cards.** Available now reads "✓ Netflix" (the check carries the meaning, so the word "Available" isn't repeated on every card); rent/buy and "Needs X" are unchanged; watched cards still show "★ 8/10 · Review". Titles blocked by a missing service are no longer dimmed while selecting, so the selected state reads clearly.

Tested (headless Chromium, 390×844 touch and 1280×800, 438-title seeded library, stub `pal-shared.js` that records every upsert/tombstone): 76 checks, all passing, zero JS errors, no horizontal overflow. Covers every status × filter combination (30) against an independent recount from the raw stored data, plus the named cases Watched→Available, Watched→Favourites, Want to Watch→New Season and All→Unavailable, and search; normal-mode cards have no controls; tap behaviour in both modes; select all on a small filtered set (8 films), on a paginated set (60 of 108, then 108 after Show more) and prune-on-narrowing; multi favourite (add, then Remove favourite, mixed selection); multi mark watched (data, heading, sync, no confirmation); multi delete (confirmation wording, decline, accept, tombstones in memory, localStorage and sync); single delete from detail (wording, cancel, confirm, sync); deleting everything in a filtered view leaves a clean empty state; Cancel, Esc and tab-switch exits; discovery cap and See all both ways. Not tested: the real `pal-shared.js` and live Supabase, live TMDB, the launcher iframe, a real iPhone, or your real library (card density was reviewed against seeded data only, since your actual titles weren't available to me).

## v2.0 (FTT-020) — Library redesign: one combined Library, simple cards, a proper title view

Information-architecture and presentation redesign per the Library UX brief. **No data-model change**: no field renamed, added or removed, nothing new is stored, and existing titles, ratings, reviews, seasons progress, services and availability are read exactly as before. Sync, the three importers, the new-season checker, service merge, JSON backup/restore and the whole edit modal are untouched (51 of the functions that carry that logic were diffed against v1.12 and are byte-identical; the only two that changed, `toggleSelectMode` and `toggleSelect`, differ solely by calling `renderLibrary()` instead of `renderFilms()`).

**Navigation.** Tabs are now **Library** and **Services**. Films → Library; the Reviews tab and its panel are gone. There is no separate Films or TV destination — they are filters.

**Library screen, top to bottom.** (1) *Search my library* with a separate **+ Add title** button beside it — TMDB search now lives in that button's dialog (with "Enter manually" alongside), so library search and TMDB search can never be confused. (2) **Want to Watch / Watched / All** as the primary switch, with counts. (3) One row of secondary filters: **All · Films · TV · Available · Favourites**, plus **More ▾** pinned at the right (a bottom sheet on phones) holding **Unavailable, Cinema, Short / Bedtime, New season, Reviewed**. (4) Compact horizontally-scrolling **Available to watch** and **New seasons** rows, each with a count and "See all →"; each is hidden when empty, and both hide while searching or filtering so they never sit between you and a filtered result. (5) **My library** with a Sort control (same seven options; default Recently added) and Select. The stat-box row and the five large curated preview grids are gone; their information lives in the counts, the discovery rows and the filters. Opens on **Want to Watch** (one constant, `lib.status`, if you'd rather it open on All).

**Cards.** Poster (now true 2:3), title, "year · Film/TV", and one contextual line — the owned service (green) or "Rent / buy" / "Needs X" for unwatched titles, and "★ 7/10 · Review" for watched ones. Favourite (♥), cinema (🎟️), new season (NEW S3) and, in the All view, watched (✓) are small poster indicators. No card borders, no per-card buttons. The unwatched-and-blocked poster dims; watched titles no longer dim for lacking an owned service. Ratings show as x/10 because that is how they are stored and edited.

**Title detail.** Tapping any card opens a full-screen detail layer (← Library returns to the same scroll position; Esc also closes it): poster, title, year · type · seasons/runtime, ♥ Favourite and ✓ Mark watched, overview, Available on (owned services highlighted), Cinema date when relevant, rating, full review, viewing history (last watched, times watched), TV progress per season with episode counts, an "Update tracked count" button for new seasons, and notes. Film pages simply omit the TV sections. **Edit title** (top right) opens the existing, complete edit modal unchanged. Delete, episode-level ticking, manual availability edits and the rest stay in there.

**Deliberate behaviour changes — please check these.**
1. **Cinema now means "in cinemas recently or coming soon".** `tmdbToTitle` stores a release date on every film, so the old badge and filter matched essentially every film. The 🎟️ indicator and the Cinema filter now use unwatched films released within the last 90 days or in the future (`CINEMA_WINDOW_DAYS`). Nothing stored changed, and the Films filter still lists every film.
2. **The per-card ⭐ and ✅ quick buttons are gone.** Favourite and Mark watched moved to the detail view (one tap after opening), and Select mode still bulk-favourites, bulk-marks-watched and bulk-removes. The detail's Watched button is one-way on purpose (an unwatch would drop the rating and review, as switching status in the edit modal already does).
3. **Grid paging.** The grid renders 60 titles at a time with "Show more", since a 1,000+ title library rendered as one page is slow on a phone. Filters, search and counts still cover the whole library.
4. **New "Reviewed" filter** (under More) keeps a browsable list of reviewed titles now the Reviews tab is gone; combine it with the My rating sort.
5. Favourite is ♥ everywhere (including the edit modal's chip and the bulk bar) so it can't be confused with the ★ rating.

**Layout notes.** Poster grid is 3 columns on a phone and auto-fills on desktop; the filter row is a single line that scrolls sideways with More pinned; the controls block is sticky on desktop only (on a phone it would take a third of the screen); the bulk-action bar is fixed to the bottom of the viewport so it stays reachable in a long list.

Tested: `node --check` on both inline script blocks; the id/onclick/getElementById cross-reference and duplicate-id/duplicate-function scans (all clean). Run in headless Chromium (390×844 touch and 1280×800) with a stub `pal-shared.js` and a seeded 438-title library: all ten filters' counts match an independent recomputation from the raw data; status × filter × search × sort; Show more; More sheet; detail → Edit → Save round trip (detail refreshes); Update tracked count; Mark watched; select mode and bulk bar; Add dialog including the "Already added — view" path; Esc/back; export → wipe → import round trip (438 titles, 7 services); browsing leaves the stored JSON byte-identical; zero JS errors and zero horizontal overflow at both sizes. ## v1.8 (FTT-013) — Shared sync between Pete and Lex (needs pal-shared.js v1.12)

**Bug:** Lex could open the tracker through the hub and the sync chip read "Synced", but she saw no titles. Diagnosed from the live database: the RLS policies on `pal_film_tracker` already allowed both user ids, and Pete's rows were all there — but `PalSync` was strictly per-user. `fetchTableRows()`, `upsert()`'s PATCH and the compaction filters all hard-coded `user_id=eq.<me>`, so each user only ever saw rows they had written themselves. Lex's pull returned nothing, "succeeded", and wrote a lone `__settings__` row under her own id (visible in the table).

**Fix, in two places:**

- `pal-shared.js` v1.12 adds an **opt-in** `shared: true` option to `table()` and `fetchTableRows()`. Shared reads drop the `user_id` filter (RLS remains the security boundary) and collapse duplicate `record_key`s to the newest `updated_at`. Shared upserts PATCH by `record_key` alone and never send `user_id` on the PATCH, so an edit updates the existing row in place — no forked copy, no change of ownership — while a genuinely new record is still POSTed under the caller's id. The flag is carried through the 401 retry queue. Every other app is unchanged: without the flag the code paths are identical to v1.11. Compaction stays per-user.
- `film-tv-tracker.html` v1.8 uses shared mode for titles, services and the settings row.

**Second issue found while fixing it — duplicate services.** A fresh device seeds the 12 default services with random ids. Once shared reads work, Lex's first pull would have merged those with Pete's existing services and pushed them up, doubling every service. `syncPull()` now drops a local service that is an untouched default (`hasAccess` false, no notes), is not in the cloud by id, and whose name the cloud already has — live or tombstoned, so a service Pete deleted stays deleted. Edited defaults, custom services, and defaults the cloud doesn't have are kept.

**Consequences worth knowing:** services and settings are now household-level — if Lex marks Netflix as "I have access", Pete sees that too. Titles are shared, including status, favourites, ratings and notes; last-write-wins per record, as elsewhere in the suite. The old stray `__settings__` row under Lex's id is harmless (newest wins, and the next settings write updates both).

**Merged onto v1.7:** built on top of the v1.7 changes (FTT-010..012 — auto-complete, new-seasons checker, per-tab search, Watched multi-select), which are untouched. ## v1.5 (FTT-008) — Generic JSON import for viewing history and watchlist

Pete's direct request: a JSON-based import (he doesn't have the source file yet, but wanted the mechanism ready) for two separate cases — viewing history (mark watched) and watchlist (want to watch) — reusing the CSV importer's matching/dedupe machinery rather than a parallel implementation.

**Schema, deliberately lenient** since the exact source isn't known yet: accepts a bare JSON array, or `{"titles": [...]}`; each entry can be a plain string or `{"title":"…","year":2020,"type":"movie"}` (`year`/`type` both optional — a year disambiguates a common title, a type skips guessing film vs TV and searches TMDB's typed `/search/movie` or `/search/tv` endpoint directly instead of `/search/multi`). Verified standalone under Node against all three shapes (bare array, wrapper object, and malformed/empty input) before wiring it into the app.

**Dedupe rules, per Pete's spec exactly:**
- *Viewing history import:* a title already in the library that isn't yet watched gets flipped to watched; one already watched is a true duplicate and is skipped (counted, not silently lost); a title with no existing match gets a full TMDB details fetch and is added as watched.
- *Watchlist import:* a title already in the library in **any** status is left alone — never downgrades something already watched back to watchlist, and never duplicates something already on the watchlist. Only genuinely new titles get added, as watchlist.
- Either way, matching happens by TMDB id after resolving the search (not raw text), so "Dune" vs "Dune (2021)"-style spelling differences don't create false non-duplicates. Anything TMDB can't match at all is still added — flagged in its notes for manual review, same convention as the CSV importer — rather than dropped.

**Refactor, not a third copy-pasted importer:** the Netflix CSV importer's progress/cancel UI (`netflixImportControls`/`Running`/`Progress` ids) was renamed to the generic `importControls`/`importRunning`/`importProgress` and is now shared by all three import buttons — only one can run at a time regardless, so one progress area is simpler than three near-identical ones. `cancelNetflixImport()`/`_netflixImportCancel` were renamed to `cancelImport()`/`_bulkImportCancel` for the same reason. `importNetflixCSV()`'s own logic is untouched beyond the id/name updates.

Tested: `node --check` on both script blocks, a full id cross-reference, an HTML tag-balance check, and the JSON parser run standalone against all three documented input shapes plus two error cases — all pass. Not tested live: the actual TMDB matching (same standing limitation as the CSV importer — no network path to api.themoviedb.org from the build sandbox), and there's no real source file yet to try an end-to-end import against.

## v1.3 (FTT-006) — Netflix history import, "times watched"

Pete uploaded a real Netflix "Viewing history" CSV export (`NetflixViewingHistory.csv`, ~3,060 rows) and asked for it to populate historical watched data: no duplicates (a count instead, for rewatches), and season-level rather than episode-level marking for TV.

**Parsing.** Netflix's export has no structure beyond `Title,Date` — a proper quoted-CSV parser was needed (some titles contain commas, e.g. "Subways, Bicycles and Automobiles"). The `Title` column itself conflates show name, season, and episode with no consistent delimiter: verified against Pete's actual file that splitting each title on `": "` and looking for a `Season N` / `Series N` / `Limited Series` / `Miniseries` segment cleanly resolves 166 shows across 277 distinct (show, season) pairs — that part is unambiguous. The remaining 1,060 distinct strings have no season marker at all, and are a genuine mix of real films (`Freefall: A Reckoning for Boeing`) and anthology/documentary-series episodes with no season label in the export (`Mating Season: The Wolf Wedding`, `Untold Mr. T: I Pity The Fool`) — text alone can't reliably tell these apart.

**Matching heuristic (imperfect, documented rather than papered over).** For the 166 explicit shows: search TMDB for the show name, require a `media_type: 'tv'` result, done. For the 1,060 ambiguous strings: first try the text before the first `": "` as a candidate show name, but only accept it if TMDB's top result is a TV show whose name matches that candidate *exactly* (case/punctuation-insensitive) — this correctly catches "Mating Season" and similar. If that fails, fall back to searching the *entire* raw string and accepting whatever TMDB returns (film or TV), which is why a docuseries with a colon in its own official name (`Turning Point: Generation 9/11`) still resolves correctly even though the naive first-colon split would have broken its name in half. Anything with no TMDB match at all is still added — as a plain watched title using the CSV's exact text, flagged in its notes for manual review — rather than silently dropped.

**No duplicates.** Every resolved show/film is checked against the existing library by TMDB id before creating anything: a show already in the library gets its new seasons merged in (not a second Title record); a film already in the library gets `timesWatched` incremented instead of a duplicate entry. A season is recorded via a new lightweight `seasonsProgress[n] = { manuallyMarkedWatched: true, episodeList: [], … }` shape — deliberately *not* fetching each season's real episode list during import (that would be another TMDB call per season per show, and Pete explicitly didn't want episode-level import). `seasonsWatchedSummary()` and the modal's season list both treat `manuallyMarkedWatched` as "fully watched"; if the title's own "Load / refresh season data" is used later, real episode data is merged in and — specifically for a season that was only ever whole-season-marked — every episode in it is promoted to watched rather than the season appearing freshly empty.

**New `timesWatched` field.** Added to the Title record and a "Times watched" input in the modal's watched-fields section (editable like anything else); watched cards now show "Watched ×N" in their meta line when N > 1.

**Scale and safety.** ~1,226 unique shows/films to resolve, up to 2 TMDB searches + 1 details call each — a deliberate one-request-at-a-time loop (150ms spacing, not because of a documented TMDB rate limit, just politeness) means a history this size takes several minutes; the Data Modal shows a live added/merged/unmatched count and a Cancel button. Local storage is saved after every processed row (so a cancelled or interrupted run keeps everything done so far); cloud sync is one bulk push of everything touched, at the end or on cancel, not interleaved per-row.

Tested: the deterministic parsing/grouping half (CSV parser + the show/season-marker split) was ported into a standalone Node script and run directly against Pete's actual uploaded file — confirmed 166 shows / 277 (show, season) pairs / 1,060 atomic strings, matching an independent Python analysis of the same file exactly. `node --check` on both inline script blocks, a full id cross-reference, and an HTML tag-balance check all pass. Not tested, and impossible to test from the build sandbox (no network route to api.themoviedb.org): the live TMDB matching itself — the exact-name heuristic, the fallback full-string search, and how well real search results behave across all ~1,226 unique entries. Recommend a first run on the real file and a skim of the Data Modal's final added/merged/unmatched counts before assuming it's clean; the unmatched bucket and any obviously-wrong merges are easiest to spot and fix right after that first run.

## v1.1 (FTT-002) — Modals were unclosable

`pal-shared.js`'s own `closeModal(id)` removes an `open` class — the convention Claim Tracker/Gym Tracker use (`.modal.open`). This app copied `test-issues.html`'s `.modal-overlay.hidden` convention instead (add/remove `hidden` on the overlay), so every call to the shared `closeModal()` throughout this file was a silent no-op: it was removing a class (`open`) the overlay never had, while the class that actually controls visibility (`hidden`) was never touched. Fixed by declaring this file's own `closeModal(id)` after `pal-shared.js` loads (function declarations in a later `<script>` win over an earlier same-named one on the same global) — every existing call site needed no changes. Also added: a visible ✕ close button on both modals (the backdrop-click target was only ~16px wide on a phone — real, but too easy to miss) and an Escape-key handler as a third way out on desktop.
