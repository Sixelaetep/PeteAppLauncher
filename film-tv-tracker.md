## v2.7 (FTT-039) — Local cache trim on sync

Same mechanism as Test & Issues' TI-086, part of a suite-wide rollout to every app using `PalSync.table()` — see `pal-shared.js`'s `trimIfLarge()` for the shared implementation and its own reasoning.

**Genuinely different situation here, worth being upfront about.** `ftt_v1`'s ~1.2MB is your *actual current library* — real titles, synopses, tags, season data from TMDB imports — not accumulated stale history the way Test & Issues' size was. Trimming and re-pulling here can't reduce anything; it would just re-fetch the same ~1.2MB straight back from Supabase. Wired in anyway, as Pete's explicit call, as a safety net against future *unbounded* growth rather than an active fix for today's size. Threshold set at 2048KB — deliberately well above the current real size, so this won't fire on a normal boot, only if the library (or something else) grows unexpectedly large.

**Wiring:** `onSession` made `async`, trim call added after `syncPull()` completes — never before, and never in `onNoSession` (no Supabase session there to restore from, so trimming would be real data loss). Same safety shape as TI-086: skips entirely if `PalSync.retryQueueLength()` shows anything still pending.

Files changed: `film-tv-tracker.html` only (`pal-shared.js` itself already shipped with TI-086 — this just adopts it here too).

**Tested:** `node --check` passes. `trimIfLarge()`'s own logic (all four branches, including the critical pending-writes-blocks-trim case) was already verified in Node against synthetic data as part of TI-086 — not re-tested per-app, since the function itself doesn't change between apps, only the key/threshold passed in.

**Not tested:** not yet run in a real browser against real Film & TV Tracker data.

## v2.6 (FTT-038) — Reorder list stays put when you change a title's Interest

**No data, sync or backup change.** In the grouped reorder list, choosing a level in a row's Interest menu still moves the title to the end of its new group (saved and synced at once, reorder mode stays open), but the screen **no longer jumps to the new position**. The page is kept so that the rows around where you made the choice (e.g. in Unrated) stay exactly where they were on screen; the row that was below the changed one (or above it, if it was last) takes its place. The moved row is still flashed briefly in its new group, and the toast names the new level, but nothing scrolls to it. Applies only to the Interest menu; ↑ ↓, drag and Move to position still keep the moved row in view.

## v2.6 (FTT-037) — Interest groups for the Available to watch queue

**Interest decides the group; manual order decides the order within it.** One new optional per-title field, `interest`: `'high' | 'medium' | 'low'`; missing = **Unrated**. It is user-set only (never inferred from TMDB, genres, ratings or availability), has no scores or stars, and is independent of `favourite`, `favouriteOrder` and `watchlistOrder`, none of which change meaning. **No migration write**: existing titles have no field, which already reads as Unrated (verified: nothing is rewritten or re-stamped on load, so `state.version` is unchanged), and new titles start Unrated. It rides localStorage, Supabase (per title, like every field) and JSON export/import.

**Ordering.** The Available to watch queue (available, Want to Watch, non-favourite) is ordered **High → Medium → Low → Unrated**, then `watchlistOrder` within each group. The same order drives the Want to Watch tab, the Available pill and the Interest filters (favourites still come first there, in favourite order). Changing a title's Interest puts it at the **end of its new group** (it takes the next free `watchlistOrder`). A reorder inside one group is written among the numbers that group already holds, so a reorder in High never touches Medium, Low or Unrated, and only the titles that actually moved are stamped and synced.

**Normal shelf.** Still compact poster tiles, now one shelf per group with a small heading and count (High interest · 6, Medium interest · 12, Low interest · 4, Unrated · 9). Each shows at most 8 tiles, and a group with more has its own **See all** / Show less (expands only that group). If nothing has an Interest yet (everything Unrated, which is every existing library on first open) it is one plain shelf with no headings, exactly as before. No Interest controls appear on any tile.

**Reorder.** The dense reorder list is now grouped: a heading per non-empty group, each its own list **numbered from 1**, with ↑ ↓ that stop at the group's ends, drag within the group, and **Move to position** clamped to the group. Each row also has a small **Interest menu** (High interest / Medium interest / Low interest / Unrated). Choosing another level moves the row into that group's end at once (saved and synced like any edit, flagged briefly so you can find it, reorder mode stays open); the rest of the draft order is untouched and nothing else is written until **Done**. Cross-group drag is not supported (the menu is the way to move between groups; the optional item in the brief). Pressing the menu never starts a drag.

**Quick edit.** Detail shows an **Interest** row (High, Medium, Low, Unrated; current highlighted) on Want to Watch titles: one tap sets it, saves and syncs. In Selection mode a new **◐ Set interest…** action opens a small sheet (one chooser instead of four buttons) and applies it to the selected Want to Watch titles, so a first pass over a long unrated list is "select these six, High". Nothing is added to the poster cards.

**Filters.** More now has **High interest**, **Medium interest**, **Low interest** and **Unrated**: Want to Watch titles with that level, including favourites and unavailable ones, as compact tiles, favourites first then queue order. No new pill, no toolbar. Search and Tags are unchanged; Interest is not a search term.

**Favourite / availability / watched.** Interest is retained through all of them. A favourite leaves the queue (Favourites has no groups); un-favouriting returns it to its group at its previous place (unless its Interest was changed meanwhile, then the end of the new group). A title that becomes unavailable moves to Unavailable keeping Interest and order, and returns to its group and place when available again. A watched title keeps its Interest and number; moved back to Want to Watch it returns to its group and place. The Detail Interest row is shown only for Want to Watch titles.

**Decisions to be aware of.** (1) Unrated rows in the reorder list **are numbered** (the brief's sketch shows them unnumbered); a blank number would have removed Move to position and the reorder feedback for every existing library, all of which starts entirely Unrated. (2) With the Interest menu each reorder row is about 76px (was about 62px) on one-line titles. (3) The Set interest… bulk action is an addition beyond the brief, kept to one button.

Heading "Reorder Available to watch · 30" with **Done**; one ~62px row per title, in the page (no inner scroll box, so a long list scrolls with the page and every position is reachable): **☰ handle** (42×52 touch target) · **position number** · small poster thumbnail · title (up to two lines) · year / film or TV / where it can be watched · **↑ ↓** (38×40, disabled at the ends). - **Drag** (pointer events, mouse, pen and touch). On a phone only the ☰ handle drags, so swiping anywhere else on a row scrolls the list; with a mouse the whole row drags (↑ ↓ and the number are plain buttons). The row you hold becomes a floating copy; the gap it leaves is a dashed empty slot showing exactly where it will land; numbers renumber live. Near the top or bottom edge the page auto-scrolls (the top zone starts just below the sticky header, so rows under it are never the drop target), so a row can be carried across a 30-title list.

A title marked watched or made a favourite mid-reorder drops out of the list and the numbers stay contiguous.

**A reorder now writes less.** The titles you rearrange move among the numbers they already hold; every other title keeps its exact number, so only titles that actually moved are stamped and synced. (Before, a reorder renumbered the whole list 1..n, which also rewrote hidden favourites and unavailable titles.) If existing numbers have ties or gaps that make that unsafe, it falls back to renumbering 1..n. Applies to both orders.

## v2.2 (FTT-032) — Ordered Want to Watch, the new Library hierarchy, and lightweight personal tags

Built from the v2.11 file (the last one delivered; no other file was supplied with the request). The brief asks for the label **v2.2**, which reads lower than v2.11; it is used as asked, in one place (title, header badge, code banner). **No sync-table, backup-format or service change.** Two new optional per-title fields (`watchlistOrder`, `tags`) ride Supabase and the JSON backup with the title like every other field.

**Library, top to bottom (unfiltered, unsearched).** Small shelves: **My favourites** (Reorder) → **Want to Watch** (Reorder, new) → **Available to watch** → New seasons (when there are any). Then **All titles** in three full-size groups: **Want to Watch**, **Unavailable now**, **Watched**. Shelves hide while searching, filtering or selecting, as before; the Want to Watch shelf also hides in the Watched view.

**Want to Watch order.** New per-title `watchlistOrder` (1 = first), independent of `favouriteOrder`. Every Want to Watch title carries one, favourites included, so a favourite keeps its queue slot while the Favourites shelf represents it.
- *Shelf.* Non-favourite Want to Watch titles only, in queue order, so nothing shows twice. Heading "Want to Watch · N"; shows 8 with **See all →** (opens the Want to Watch tab); any availability (an unavailable title can be in your queue; it is listed under Unavailable now in All).
- *Reorder.* Same machinery as the favourites reorder, generalised to two collections (`favKind`: `fav` | `queue`): pointer-event drag, ☰ handle on touch (the rest of the tile scrolls), edge auto-scroll, ← / → keys, no tap-to-open while reordering, and Done. Reorder lays out the **whole** queue, not just the 8 shown. One reorder at a time: starting another saves the first. The titles you rearrange move among the slots they already occupy, so favourites' internal slots and everything outside the set stay put; only titles whose number changed are renumbered, saved and pushed.
- *Adding.* A new Want to Watch title (add, import, edit, tagging) appends to the end. A new favourite that is also Want to Watch gets an internal slot but stays off the shelf.
- *Favourite on / off.* Favouriting removes it from the shelf; un-favouriting returns it to its **existing** place (verified mid-queue), not the bottom.
- *Watched.* Marking watched takes it out of the active queue and **keeps** its number; returning it to Want to Watch restores its place (if another title now holds that number the tie is broken deterministically, and the next reorder renumbers cleanly).
- *Upgrade.* Existing `favouriteOrder` is untouched. Titles without `watchlistOrder` are numbered once, continuing the order Want to Watch was already displayed in (favourites, then available, then the rest newest-first), silently: no `updatedAt` change, nothing pushed, written to storage on first open so exports carry it. Verified: no existing field on any title changes. Two devices numbering the same data independently reach the same result unless their services settings differ at that moment; the first reorder on either device overwrites with a synced order.

## v1.5 (FTT-008) — Generic JSON import for viewing history and watchlist

Pete's direct request: a JSON-based import (he doesn't have the source file yet, but wanted the mechanism ready) for two separate cases — viewing history (mark watched) and watchlist (want to watch) — reusing the CSV importer's matching/dedupe machinery rather than a parallel implementation.

**Schema, deliberately lenient** since the exact source isn't known yet: accepts a bare JSON array, or `{"titles": [...]}`; each entry can be a plain string or `{"title":"…","year":2020,"type":"movie"}` (`year`/`type` both optional — a year disambiguates a common title, a type skips guessing film vs TV and searches TMDB's typed `/search/movie` or `/search/tv` endpoint directly instead of `/search/multi`). Verified standalone under Node against all three shapes (bare array, wrapper object, and malformed/empty input) before wiring it into the app.

**Dedupe rules, per Pete's spec exactly:**
- *Viewing history import:* a title already in the library that isn't yet watched gets flipped to watched; one already watched is a true duplicate and is skipped (counted, not silently lost); a title with no existing match gets a full TMDB details fetch and is added as watched.
- *Watchlist import:* a title already in the library in **any** status is left alone — never downgrades something already watched back to watchlist, and never duplicates something already on the watchlist. Only genuinely new titles get added, as watchlist.
- Either way, matching happens by TMDB id after resolving the search (not raw text), so "Dune" vs "Dune (2021)"-style spelling differences don't create false non-duplicates. Anything TMDB can't match at all is still added — flagged in its notes for manual review, same convention as the CSV importer — rather than dropped.

**Refactor, not a third copy-pasted importer:** the Netflix CSV importer's progress/cancel UI (`netflixImportControls`/`Running`/`Progress` ids) was renamed to the generic `importControls`/`importRunning`/`importProgress` and is now shared by all three import buttons — only one can run at a time regardless, so one progress area is simpler than three near-identical ones. `cancelNetflixImport()`/`_netflixImportCancel` were renamed to `cancelImport()`/`_bulkImportCancel` for the same reason. `importNetflixCSV()`'s own logic is untouched beyond the id/name updates.

Tested: `node --check` on both script blocks, a full id cross-reference, an HTML tag-balance check, and the JSON parser run standalone against all three documented input shapes plus two error cases — all pass. ## v1.4 (FTT-007) — Season progress denominator fix, every season shown

## v1.3 (FTT-006) — Netflix history import, "times watched"

Pete uploaded a real Netflix "Viewing history" CSV export (`NetflixViewingHistory.csv`, ~3,060 rows) and asked for it to populate historical watched data: no duplicates (a count instead, for rewatches), and season-level rather than episode-level marking for TV.

**Parsing.** Netflix's export has no structure beyond `Title,Date` — a proper quoted-CSV parser was needed (some titles contain commas, e.g. "Subways, Bicycles and Automobiles"). The `Title` column itself conflates show name, season, and episode with no consistent delimiter: verified against Pete's actual file that splitting each title on `": "` and looking for a `Season N` / `Series N` / `Limited Series` / `Miniseries` segment cleanly resolves 166 shows across 277 distinct (show, season) pairs — that part is unambiguous. The remaining 1,060 distinct strings have no season marker at all, and are a genuine mix of real films (`Freefall: A Reckoning for Boeing`) and anthology/documentary-series episodes with no season label in the export (`Mating Season: The Wolf Wedding`, `Untold Mr. T: I Pity The Fool`) — text alone can't reliably tell these apart.

**Matching heuristic (imperfect, documented rather than papered over).** For the 166 explicit shows: search TMDB for the show name, require a `media_type: 'tv'` result, done. For the 1,060 ambiguous strings: first try the text before the first `": "` as a candidate show name, but only accept it if TMDB's top result is a TV show whose name matches that candidate *exactly* (case/punctuation-insensitive) — this correctly catches "Mating Season" and similar. If that fails, fall back to searching the *entire* raw string and accepting whatever TMDB returns (film or TV), which is why a docuseries with a colon in its own official name (`Turning Point: Generation 9/11`) still resolves correctly even though the naive first-colon split would have broken its name in half. Anything with no TMDB match at all is still added — as a plain watched title using the CSV's exact text, flagged in its notes for manual review — rather than silently dropped.

**No duplicates.** Every resolved show/film is checked against the existing library by TMDB id before creating anything: a show already in the library gets its new seasons merged in (not a second Title record); a film already in the library gets `timesWatched` incremented instead of a duplicate entry. A season is recorded via a new lightweight `seasonsProgress[n] = { manuallyMarkedWatched: true, episodeList: [], … }` shape — deliberately *not* fetching each season's real episode list during import (that would be another TMDB call per season per show, and Pete explicitly didn't want episode-level import). `seasonsWatchedSummary()` and the modal's season list both treat `manuallyMarkedWatched` as "fully watched"; if the title's own "Load / refresh season data" is used later, real episode data is merged in and — specifically for a season that was only ever whole-season-marked — every episode in it is promoted to watched rather than the season appearing freshly empty.

**New `timesWatched` field.** Added to the Title record and a "Times watched" input in the modal's watched-fields section (editable like anything else); watched cards now show "Watched ×N" in their meta line when N > 1.

**Scale and safety.** ~1,226 unique shows/films to resolve, up to 2 TMDB searches + 1 details call each — a deliberate one-request-at-a-time loop (150ms spacing, not because of a documented TMDB rate limit, just politeness) means a history this size takes several minutes; the Data Modal shows a live added/merged/unmatched count and a Cancel button. Local storage is saved after every processed row (so a cancelled or interrupted run keeps everything done so far); cloud sync is one bulk push of everything touched, at the end or on cancel, not interleaved per-row.

Tested: the deterministic parsing/grouping half (CSV parser + the show/season-marker split) was ported into a standalone Node script and run directly against Pete's actual uploaded file — confirmed 166 shows / 277 (show, season) pairs / 1,060 atomic strings, matching an independent Python analysis of the same file exactly. `node --check` on both inline script blocks, a full id cross-reference, and an HTML tag-balance check all pass. Not tested, and impossible to test from the build sandbox (no network route to api.themoviedb.org): the live TMDB matching itself — the exact-name heuristic, the fallback full-string search, and how well real search results behave across all ~1,226 unique entries. Recommend a first run on the real file and a skim of the Data Modal's final added/merged/unmatched counts before assuming it's clean; the unmatched bucket and any obviously-wrong merges are easiest to spot and fix right after that first run.

## v1.1 (FTT-002) — Modals were unclosable

`pal-shared.js`'s own `closeModal(id)` removes an `open` class — the convention Claim Tracker/Gym Tracker use (`.modal.open`). This app copied `test-issues.html`'s `.modal-overlay.hidden` convention instead (add/remove `hidden` on the overlay), so every call to the shared `closeModal()` throughout this file was a silent no-op: it was removing a class (`open`) the overlay never had, while the class that actually controls visibility (`hidden`) was never touched. That's the exact bug behind "stuck in the modal" — Cancel, the click-outside handler, and (this release's own addition) a new ✕ button were all correctly wired, but all three called a function that did nothing to this markup. Fixed by declaring this file's own `closeModal(id)` after `pal-shared.js` loads (function declarations in a later `<script>` win over an earlier same-named one on the same global) — every existing call site needed no changes. Also added: a visible ✕ close button on both modals (the backdrop-click target was only ~16px wide on a phone — real, but too easy to miss) and an Escape-key handler as a third way out on desktop.
