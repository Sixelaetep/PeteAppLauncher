# Fantasy Football Tracker — Change Log

Single source of truth for release history of `fantasy-football-tracker.html`. Newest first.
The same entries live in the changelog comment at the top of the app's script block; keep the two in step on every release.
Versions are mirrored in five places: `<title>`, the nav badge (`#navVer`), `pal-shared.js?v=`, the `FF_VERSION` constant, and the export backup `appVersion` (which reads `FF_VERSION` from v1.48).

## v1.48 — FF-020

Locked-in / planned transfers no longer linger once the same transfer is confirmed by FPL. ROOT CAUSE: in syncTransfersFromFPL() the "already in the log" check (existingIds.has(id) → return) ran BEFORE the step that upgrades a matching planned/locked-in entry. So once an FPL transfer had been synced into the log, it could never absorb a locked-in entry that existed (or was created) afterwards — the manual entry stayed alongside its confirmed twin forever, double-counting in the running total and the free-transfer slot usage. Separately, pullRemoteTransferLog() merges by id (union), so a manual entry removed on one device could be resurrected from another device's copy. FIX: new reconcileTransferLog() — one idempotent pass that pairs each manual planned/locked/made entry with a synced FPL ('auto') entry for the same player out + player in (one-to-one, so a genuine second identical swap is not swallowed; ignores FPL transfers from a gameweek clearly before the plan), keeps the FPL entry as the source of truth (real date, cost, gameweek, rating support), carries the manual entry's note across if the FPL one has none, and removes the manual one. It runs after every sync, after loading the log from cache, after the cross-device merge (and re-persists if it changed anything, so Supabase heals too) and when a lock-in is added for a swap FPL already shows. Sync no longer does its own in-place upgrade — it adds new FPL entries and lets the same reconcile pass do all matching, so there is exactly one code path. Also fixed: the export backup's appVersion was a hard-coded '1.46' that had drifted; it now reads FF_VERSION. No data-model change, no Supabase schema change, existing logs heal automatically on first load.

## v1.39 — FF-016

Reported directly: free transfers showing 0 remaining with nothing actually transferred this window. Root cause was in computeTransferSlotUsage() — it counted EVERY active (locked/planned) transfer-log entry ever logged, with no gameweek scoping at all, so an entry that was never explicitly resolved (marked made, or auto-matched by Sync from FPL) went on silently consuming every future gameweek's free-transfer budget forever. addManualTransfer() now stamps gwId at creation (previously only set once an entry later became 'made'), and computeTransferSlotUsage only counts entries tagged for the CURRENT planning gameweek — anything else active is reported as staleActiveCount rather than silently dropped, with a new banner in the Transfers tab explaining how many there are and pointing at Sync from FPL (auto-resolves genuine matches) or manual review/delete. Entries logged before this fix all have gwId: null and fall out of the count immediately.

## v1.33

reported directly: Lex's Settings tab showed Pete's real FPL entry ID. Root cause was architectural, not cosmetic: every per-user localStorage key (ff_settings_local, ff_squad_cache, ff_score_history, ff_advice_cache, ff_transfer_log, ff_external_check, ff_manual_lineup) was a plain shared-browser key with no per-user scoping at all — added when the app was still single-user, never revisited when multi-user support (KNOWN_USERS/ RLS) was added. Supabase itself was never at risk — RLS (auth.uid()=user_id on every table) means one person's session can never read or write another's row no matter what's cached locally — but the local DISPLAY could show one person's data to another, and a save from that state would write the wrong value into THEIR OWN row.

Fixed: every one of those 7 keys is now suffixed with the signed-in user's id via a new scopedKey() helper (ff_show_position_best deliberately excluded — it's a shared display preference, not personal data). Boot sequence restructured: per-user cache loads, which used to run unconditionally before auth had even started resolving, are now deferred until the signed-in user is actually known (onSession, onNoSession, and the no-PalSync fallback all covered). One-time migration for Pete's own existing legacy data, scoped specifically to his known user id so it can never trigger for anyone else's sign-in — the legacy shared key is removed after migrating, closing the loop for any future browser sharing too. Entry ID placeholder also changed from a real ID to a generic example, matching the one already used in the help text above it.

Tested by reproducing the actual scenario end-to-end: seeded a browser with Pete's real pre-fix legacy data, confirmed migration moves it to his scoped key and removes the legacy key, then signed Lex into that SAME browser's localStorage and confirmed she sees a genuinely empty field, his data is untouched under his own key, and her own save goes to her own key without affecting his.
