# Gym Tracker — Changelog

Full version history for `gym-tracker.html`. The app's own inline comment block keeps only the 15 most recent releases for quick reference during active work — everything else lives here. Wording is unchanged from the original inline entries. One reordering note: the source file's own history wasn't in a single consistent order (an older ascending-append run and a newer descending-prepend run were mixed together, and one version number — v2.48 — was reused for two unrelated fixes); everything below is resequenced strictly newest-to-oldest by version number so it's actually readable, with the v2.48 collision kept as (i)/(ii) in original file order. No content was reworded.

## v2.90 (GYM-082)

follow-up to GYM-081's Overall Progress score — not from a written brief, from talking through what it looked like and how to improve it. Three changes, all from that conversation: 1. Visual: the old one-line "4 improving · 2 steady..." text stat is now a colour-coded segmented bar (green=improving, gray=steady, orange=mixed, coral=declining — same colour meanings the Exercise List/PDF trend badges already use, reused rather than invented) — see progressBarAndLegend(). Sits in a new dedicated "📈 Progress Breakdown" section, replacing the cramped text line that used to live inside the Sessions/Completed/Duration hero-row. 2. Segmented by body area, not just overall: computeProgressBreakdown() now also buckets judged exercises by PRIMARY tag (tags[0] — see primaryAreaForExercise()) and shows the same bar per area, so a stall in one area doesn't hide behind an overall number averaging out fine. Each legend entry is a live link (jumpToExerciseListFiltered()) into a new trend filter on the Exercise List (All/Up/Steady/Mixed/Down), so "2 declining" is now something you can actually go look at, not just a count. 3. History: computeProgressHistory() samples the overall score at 8 points using a ROLLING 30-day window each, one week apart (not 8 disjoint 1-week buckets — a single week rarely has ≥2 occurrences of any one exercise to judge a trend from, so narrow buckets would be mostly gaps) and plots it as a small trend line, reusing sparklineSvg(). Answers the "is +38% an improvement over last month or a dip from +70%" question a single snapshot can't. Explicitly did NOT weight the score by how often an exercise is trained, after weighing it: it would let 1-2 high-frequency exercises dominate a score whose whole point is a BROAD read, it needs a weighting curve to justify and explain, and "trained often" isn't the same claim as "matters more" (a deliberately-rare weak-point exercise shouldn't count for less because it's rare). The existing ≥2-occurrence threshold already screens out one-off noise, which is the main problem weighting would otherwise solve. Recommendation, not a closed decision — see the comment above scoreFor() for the contained follow-up if this turns out wrong in practice.

## v2.89 (GYM-081)

reworked what "progress" means per exercise — this touched bestSetValue(), the one function every trend read in the app (Exercise List cards, the PDF's Progression Summary, the new Overall Progress score below) ultimately comes from. Reps/weight: was tracking weight alone, so a static weight with climbing reps never registered as progress. Now uses an estimated 1-rep-max on the best set (Epley: weight × (1 + reps/30)) — this one number rises for either weight going up (reps held) or reps going up (weight held), matching both cases described in the brief. Time/distance: which direction actually counts as progress isn't the same for every exercise (a plank getting longer is progress; a 5k getting shorter is). New per-exercise settings in the exercise editor — Progress Direction (time: Longer/Endurance vs Shorter/Speed) and Progress Basis (distance: More Distance vs Faster Pace) — default to the behaviour that already existed (longer, distance), so nothing changes for exercises nobody touches. Stored on the exercise record (not the session item), so changing the setting later re-reads every past session under the new choice rather than locking history to whatever was picked at logging time. "Overall progress across everything" — explicitly an open question in the brief, so the methodology is spelled out in the code comment above computeOverallProgressScore(): among exercises with ≥2 occurrences in the current window (enough to call a trend at all), (#improving − #declining) / #judged as a ±100% reading, shown as a new "Overall Progress" stat in Insights' Period Overview. This is a judgement call on how to blend individual trend reads into one number, not an industry-standard formula — flagged as such rather than presented as more authoritative than it is.

## v2.84 (GYM-074)

first-open sync errors — the app only ever listened passively for the launcher's PAL_SESSION postMessage. If that one-shot message and this iframe's own load timing didn't line up (network/script variance), nothing asked again: the 3s onNoSession banner fired and the app sat in local-only until the app was reopened, at which point a fresh load usually won the race. requestFreshSession() already existed for exactly this (GYM-021) but was only ever called from the 5-minute queued-retry interval, never at startup. Now also fires a few times in the first ~4s after load (every 700ms, up to 6 attempts, stopping the moment a session arrives) so a missed initial message gets several more chances instead of none. Harmless if the launcher already sent a session — hasSession() short-circuits every attempt — and this is the same message the retry-queue path already sends, so no launcher change is required for this to help.

## v2.78 (GYM-072-b follow-up)

v2.77's Copy & Send worked testing on a Mac but reportedly did nothing at all on an actual iPhone — clipboard copy succeeded, Shortcuts never opened. Root cause: a script-driven `location.href = 'shortcuts://...'` can be silently swallowed by a standalone home-screen web app on iOS, even though the exact same URL scheme works fine as a genuine link tap. ## v2.73 (PET-068 / GYM-071)

note on versioning — this uploaded file's title/badge already read v2.72 but the internal VERSION constant was still '2.71' (same drift pattern as the earlier v2.61/v2.62 reconciliation) — fixed alongside this release. Root cause of "launcher dashcard not respecting 2 decimal point max": summing decimal calorie/protein/water values in raw JS arithmetic can produce results like 12.5 + 23.05 === 35.550000000000004, and that was being displayed as-is with no rounding anywhere. fmtProtein() already existed and rounded protein correctly, but only protein — calories and water volume were never wrapped the same way. Generalised fmtProtein into a plain round2 alias (same logic, applicable to any figure) and applied it: (1) at save time in every place that parses a calorie/protein/volumeMl number from an input, so new data can't drift; (2) defensively at every sum/total and individual-value display site, so any already-stored imprecise value still renders cleanly without needing a data migration; (3) ported the same round2() into index.html's statGym() card logic — the actual reported location — since it reads gym-tracker's localStorage independently and has no access to gym-tracker's own functions. See index.html's own changelog.

## v2.72 (GYM-071)

protein figures were showing raw floating-point noise in places — reduce()-summed totals (day totals, report daily breakdown, saved-meal-search pill) can produce results like 36.85000000000001 from ordinary decimal-gram entries (e.g. 24.5g + 12.35g), and manually-typed decimal targets/entries displayed exactly as typed with no ceiling. New fmtProtein() helper rounds to at most 2 decimal places for display — a whole-gram value like 24 is untouched (never padded to "24.00"), it's a ceiling on decimals shown, not a fixed format. Applied at every read-only protein display site: Meals modal totals + per-entry list, day-card nutrition summary, saved-meal search pill and saved-meals library list, nutrition targets summary, and the PT/period report's stat cells and daily nutrition table. Deliberately NOT applied to the editable meal/target input fields (pre-filling an edit form with a rounded value would silently alter what's shown mid-edit) or to the underlying stored records — this is a display-only fix, so the JSON backup format and every stored value are completely unchanged. Note: the brief's issue title said "1 decimal point" but the body said "maximum of 2 decimal point" — implemented per the more detailed body text (2dp); flagging the discrepancy in case 1dp was actually intended, since it's a one-line change to fix.

## v2.51 (GYM-047, third and actual root cause)

re-importing the same backup kept losing its real notes on every subsequent sync, even after the v2.49 dedup fix and the v2.50 race-condition fix — both of those were real bugs and both are correctly fixed, but neither protects against this: the cloud very likely already holds a corrupted copy of the real note set (marked archived, from when the original v2.48 bug ran and auto-pushed that mistake) with a timestamp NEWER than anything in the backup file. A plain last-write-wins merge would keep letting that corrupted-but-newer cloud copy win, no matter how many times the same backup gets re-imported — the file's own embedded updatedAt can never out-date corruption that happened after it was exported. Also found: importJSON() never defaulted trainerNoteSets at all (every other field had a fallback) — a backup missing that field entirely would leave it undefined and crash the first read. Fixed: on import, trainerNoteSets now defaults properly, every note set's updatedAt is bumped to the moment of import (guaranteeing the restore wins the next merge/push regardless of what's already in the cloud, since restoring a backup is a deliberate "this is the truth now" action), and ensureActiveNoteSet() runs immediately rather than waiting for the next sync. Documented tradeoff: if another of your devices has genuinely newer notes not yet synced, restoring an older backup here and letting it push could overwrite them once that device's edit reaches the cloud — restore is authoritative for this collection, by design.

## v2.50 (GYM-047, second root cause)

the actual bug behind "sync removed my notes again" after restoring a backup on v2.49 wasn't the dedup heuristic (that part was already fixed) — it was a genuine race condition. pullFromCloud() runs automatically the instant a session arrives, including on every app launch, before the user can do anything. If a JSON import (or Clear All Data) replaces _env while that automatic pull is still in flight, the pull was captured against the PRE-import local data the moment it started; when it finally resolved, it unconditionally overwrote the fresh import with those stale merge results, silently undoing the restore the user had just performed. New _envGeneration counter bumps on every wholesale _env replacement; a pull now captures the generation it started with and discards its own results entirely if that's changed by the time it resolves, rather than blindly applying a merge computed against data that no longer exists. Residual note: if the cloud already holds a corrupted copy from the earlier v2.48 bug (real notes flipped to archived, with a recent timestamp), a race-free sync can still show it that way — the v2.49 Restore button is the deliberate fix for that, not something this silently auto-corrects.
