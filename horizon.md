# Horizon — Changelog

Full version history for `horizon.html`. The app's own inline comment block keeps only the most recent releases for quick reference during active work — everything else lives here. Wording is unchanged from the original inline entries; only the line-wrapping is reflowed.

## v4.10 (2026-09-26)

HZN-012: joined the shared pal-utils.js rollout. Local escHtml() deleted — pal-utils.js ships an escHtml() alias that is a strict superset (also escapes single quotes via the DOM textContent/innerHTML round-trip vs pal-utils's regex approach; rendered output is identical either way, since both produce valid entity-escaped HTML). Local uid() deleted too — every call site here already builds its own compound key externally (e.g. "bucket_" + uid()), so pal-utils's uid(prefix), called bare with no prefix argument, is a safe drop-in with zero call-site changes; only the shape of freshly-generated ids changes (a timestamp+random suffix instead of a bare 7-char random one), and nothing in this app parses or validates that shape. No other local helper (toast, todayISO, closeModal) exists here to migrate. No calculation or data-model logic touched — verified via node --check and a manual reload against a real saved session (buckets, mortgage options, checkpoints all displayed unchanged). Also bumped the cache-busting query string on pal-config.js/pal-sync.js/pal-utils.js to ?v=4.10, matching the version-badge/VERSION const bump.

## v4.0 (2026-08-08)

Re-scoped around a simpler mental model, based on Pete's own description of how he actually thinks about this (three kinds of money, guaranteed income vs a backup pot, mortgage-first-then-redirect) rather than the far more elaborate death/survivor/stress-test system explored in an earlier, separate brief. Built on top of the v3.0 single-pot rewrite (still the correct foundation — two fixed scenarios, mortgage-tab-driven purchase, unified pre/post-retirement trajectory), extending the single growth pot into multiple named buckets. HZN-701 — Buckets replace the single growthPot household field. New bucket_* records: {name, monthlyAllocation, growIndefinitely, currentBalance}. Every bucket carries its own explicit £/mo — no more "100% of surplus flows automatically," since sinking funds (Holiday, House/repairs, Family/emergency — genuinely new, started empty per Pete's explicit choice, not pre-seeded) need their own budgeted amount. New computeBucketFlows(): allocations come off the top, and whatever's left sweeps automatically into the growth bucket(s) only (split evenly if more than one) — never into sinking funds, since those are deliberately bounded amounts, not "whatever's left." Sinking-fund allocations are a fixed nominal £/mo (not inflated) — a documented v1 simplification. projectScenario updated throughout: growthPot is now the SUM of every growIndefinitely-flagged bucket's balance; sinking funds are tracked and shown but completely excluded from the deposit/retirement engine. New migrateToBucketsIfNeeded(): a real pre-v4.0 growthPot balance becomes a single auto-created "Growth" bucket (currentBalance carried forward exactly, monthlyAllocation:0 since the old model's "everything flows automatically" is now expressed as pure leftover-sweep) — confirmed with a real-data test that the exact balance survives the full migration chain. New Buckets panel in Setup: add/edit/delete, a Grows indefinitely / Used regularly toggle per bucket, an over-allocation warning when buckets commit more than the actual monthly surplus. HZN-702 — "Can we calculate when you can switch [from income-needs drawdown to flat 4%] and still afford to live and not run out of money" — a calculated answer, not a manual assumption, and deliberately NOT a death/survivor simulation (no income drop, no survivor percentage, no household-phase change) — purely a change in how the drawdown number itself is calculated from the switch age onward. New computeEarliestSafe4PercentSwitchAge(): scans candidate switch ages from retirement forward, for each one re-simulating income-needs drawdown up to that age then a flat-4%-of-balance rule (same year-1-then-inflate convention DC pots use elsewhere) afterward, checking the SAME check horizon (HORIZON_AGE) everything else in the app already uses. Checks TWO conditions, not one — a real design gap caught and fixed via testing before shipping: a thin pot drawing a self-limiting 4% can easily survive to the horizon while still leaving a genuine shortfall against living costs every year, so "the pot never runs dry" alone isn't the same question as "you can actually afford to live" — both are now checked (ranOut / shortfallEver), and a candidate age only counts as safe if neither ever triggers. Verified against both a well-funded case (correctly returns the retirement age itself) and a genuinely thin-guaranteed-income case (correctly returns null — an honest "not achievable this way," not a forced number). Checkpoints updated to capture the full bucket list (not just a single total) so a saved checkpoint genuinely reflects what existed at that moment.

## v2.3 (2026-08-07)

Bug fix, found while building the end-to-end user guide: the "Discretionary net worth" contingency reserve was showing as e.g. £8,713 for what should have been a plain £15,000. contingencyReserveAtAge() was returning the raw as-entered (real, today's-money) figure directly, but everywhere it's used (netWorthDrawdownIncomeAtAge, computeAtRetirementBreakdown) treats it as nominal — subtracting a real figure from a nominal one is a unit mismatch, and toDisplay()'s real-mode deflation on the way to the screen then deflated an already-real figure a second time. Fixed the same way it was fixed once before in the v1.x line: the function now inflates the reserve to its nominal equivalent at the given age before returning, so toDisplay() correctly recovers the original figure in real mode instead of double-deflating it. This exact fix existed in v1.21 but wasn't present in the v2.x codebase built in a different session — a real regression, not a new bug.

## v2.1 (2026-08-07)

HZN-004: one-off costs learn to distinguish OWNING-SPECIFIC costs (a boiler, a roof, a rewire — only relevant once you actually own a home) from UNIVERSAL ones (a car, a laptop, a big trip — everyone pays these, renting or owning), plus a realistic 12-item starter set replacing the single v2.0 boiler example. Additive and backward-compatible — the v2.0 calculation engine, cloud sync, and v1.x/v2.0 migration are all untouched; nothing here rewrites projectScenario's, pensionIncomeAtAge's, or simulateDrawdown's core maths, only extends their inputs, exactly like v2.0's original one-off costs did. 1. New scope field. oneoff_* records gain data.scope: "all" (default) | "ownedOnly". "all" behaves exactly as every one-off did before v2.1 — applies on its timing regardless of ownership, rent baseline included. "ownedOnly" applies ONLY in years the scenario actually owns the property (from its own purchaseAge onward) — never on the rent baseline, never before that scenario's own purchase. A recurring ownedOnly cost's first occurrence is max(timing.startAge, purchaseAge), then every N years from there — so a cost nominally "due" before the purchase shifts its whole cycle to start counting from ownership itself, rather than firing retroactively. A single-age ownedOnly cost fires only if that specific age is itself already owned — otherwise it simply never happens in that scenario's timeline. Backward-compatible: oneoffScope() treats any oneoff_* record without a scope (every one saved before v2.1) as "all" everywhere it's read; a small migrateOneoffScopeIfNeeded() also backfills the explicit field on load/import for tidiness, though the fallback alone is sufficient for correctness. 2. Engine — scope applied correctly, the important part. buildOneoffSchedule() now keeps the two scopes SEPARATE rather than pre-summing: schedule.always is resolved exactly as before (timing-only, independent of ownership); schedule.ownedOnlyItems is deliberately left AS RAW ITEMS, unresolved, since ownedOnly applicability depends on purchaseAge — which for an "asap"-trigger scenario is only discovered mid-loop inside projectScenario, not known ahead of time. New ownedOnlyItemFiresAtAge() (single-age predicate, used inside projectScenario's forward loop, checked right after the purchase trigger so `bought`/`purchaseAge` already reflect this age's final state — inclusive of the exact purchase age itself, which counts as "owned by that age") and ownedOnlyOccurrencesForItem() (full-horizon resolution GIVEN a final purchaseAge, used once the loop has finished or by simulateRetirementDrawdown, which receives the scenario's already-fixed purchaseAge on scenarioResult). Both floor at 0 and respect the existing pot ring-fence exactly as scope:"all" always did. Threaded through: projectScenario (deposit/savings pots, in-loop, plus a resolved pensionExtraOutflows for any ownedOnly "from pension" cost, built once purchaseAge is final); simulateRetirementDrawdown (a retiree who never bought, purchaseAge===null, is correctly never charged ownedOnly repair costs — ownedOnlyOccurrencesForItem returns [] whenever purchaseAge is null); and the combined oneoffOccurrences list powering chart markers and the one-pager's block 3 list, which now only ever shows ownedOnly markers at ages a scenario actually owned — the rent baseline shows none of them, by construction. 3. UI. One-off modal gains a scope selector — "Applies to any scenario" vs "Only once a home is owned" — with a short helper line explaining the ownedOnly behaviour. Setup's one-off list rows now show a small "universal" / "owned only" tag so the distinction is visible without opening each item. 4. Preseeded starter set. defaultState() (fresh installs only) now includes 12 realistic one-off costs instead of the single v2.0 boiler example — 4 universal (car replacement, furniture, tech refresh, a milestone trip) and 8 owning-specific (boiler, roof, rewire, kitchen/bathroom refits, windows, external decorating, boundary/driveway/garden — see ONEOFF_SEED_LIST for the exact figures and timings). New ONE-TIME seedOneoffCostsIfNeeded() migration brings the same starter set to returning/synced sessions that predate v2.1 — fires only when the user currently has ZERO oneoff_* records of any kind (active or soft-deleted; even one existing record, including a pre-v2.1 boiler example or a previous run of this migration, means it never re-seeds on top of that) AND the new assumptions.oneoffSeeded flag isn't yet set; either way, oneoffSeeded is then set to true so the seeds never reappear once a user has edited or deleted them. Rides the normal sync pipeline as ordinary oneoff_* records + one settings flag — no schema change. TESTING — new pure helpers exposed on __horizonTestHooks (oneoffScope, ownedOnlyOccurrencesForItem, ownedOnlyItemFiresAtAge, migrateOneoffScopeIfNeeded, seedOneoffCostsIfNeeded, ONEOFF_SEED_LIST), satisfying HZN-4-T1..T4 — see the accompanying test manifest. All HZN-2.0-T1..T10 continue to pass unchanged.
