# Reading Tracker — Changelog

Full version history for the clean, contiguous changelog block in `reading-tracker.html` (lines 1787-2226 of the pre-trim file, v3.29 through v3.67). The app's own inline comment keeps only the 15 most recent releases from that block for quick reference — the rest lives here. Note: this file also has older changelog notes scattered through earlier sections of the code (short, tied to specific lines) which were left untouched — only this one clean block was archived.

## v3.52 (MR-037)

the widget's "This month's target" label was a static hardcoded string — it never switched to "This cycle's target" even when a cycle start date was set, even though the subtext underneath it ("N days left this month/cycle") already switched correctly. Now both read the same cfg.cycleStartDate check. This does NOT explain the full report (day-count itself showing calendar-month math while the Book List's own cycle-date field displayed the date correctly set) — every read of cfg.cycleStartDate in the widget and the settings panel goes through the same appState.monthlyConfig object, and nothing in this codebase resets it once set, so that half of the report needs a fresh JSON export or a repeat-after-resaving check to pin down further; noted back to Pete rather than guessed at further.

## v3.51 (MR-036)

THE bug behind the Monthly widgets never appearing on the Home Screen at all, regardless of targets/sort/reading order being set correctly (confirmed from Pete's screenshots — settings all correct, Set Adrift first in manual order, but nothing rendered between "Import books" and "My Trackers"). Both widget cards (#moBookCard/#moAudioCard) reuse the tracker screen's .now-reading-card class purely for its styling — that class defaults to display:none, only ever shown elsewhere via a .visible class the per-tracker Now Reading widget toggles. renderMonthlyWidget() was written to populate every CHILD element inside the card (title, progress, target, log row, etc.) but never once touched the card's OWN display — so the fully-populated widget sat correctly built in the DOM, permanently invisible underneath the CSS default. Fixed by explicitly setting the card's display on every render. Note the two card ids (moBookCard/moAudioCard) don't follow the p+"X" pattern used for every child id (moBTitle/moATitle etc.) — needed its own explicit lookup rather than _moPrefix(type) + "Card".

## v3.50 (MR-035)

fixes the actual bug behind "no target pages and log entry" for a book on the Book List — isBookListItemDone(w) computed highestPageForItem(w) >= (w.pages || 0); for any book added with no page count, that's 0 >= 0, true, so it was silently marked "done" and permanently excluded from bookListQueue() — it could never become the active book, so it never got a target or a log field, and there was nothing wrong-looking to notice (it just quietly wasn't there). Fixed to only complete on an explicit pages count (manualComplete still works as an independent override). - That alone would have left a 0-pages active book showing a meaningless "0 of 0, finished" — added a distinct widget state instead: "No page count set yet" with the log input repurposed to SET the total instead of logging progress (logBookListQuick/onBookListLogInput both branch on item.pages > 0 now). - addToWishlistFromView's Pages field stays optional (you may genuinely want to jot a title down before knowing its length) but now flags it in the confirmation toast, so this doesn't silently recur without at least a heads-up at add time.

## v3.49 (MR-034)

brings back a recurring "cycle start date" for the Monthly widgets — this existed briefly in v3.46 (a per-tracker field, back when Monthly Mode was still tracker-based) but was dropped entirely in v3.47's Book List rebuild without being replaced, since that rebuild changed what "Monthly" even was. Re-added as a single shared appState.monthlyConfig.cycleStartDate (not per-type — one cycle date covers both widgets), used by daysLeftInMonthlyCycle() in place of the plain calendar-month calc whenever it's set. Optional: leave it blank and the widgets fall back to counting down to the calendar month-end, same as v3.47/48's default behaviour.

## v3.48 (MR-033)

two small polish fixes from real use of v3.47. - Every remaining user-facing "Wishlist" string renamed to "Book List" — the screen header/card/button text was updated in v3.47, but several toasts, confirm() dialogs, and a tooltip were missed (moveBookToWishlist's confirm, deleteTracker's confirm, the import-target dropdown, several showToast messages). Internal names (renderWishlistView, appState.wishlist, _rtWishlist, etc.) are unchanged — purely user-facing text, to keep the risk low. - Renamed "reading goal" collections to "dated collections" — Pete asked how to set just the plain monthly target without creating one of these, which was really a naming collision: the Books/month & Pages/month number fields ARE the monthly goal and never needed a collection, but both features used "goal" language, so it read like the collection was required. No behaviour changed — collections still work exactly as before, just under a name that doesn't compete with "Monthly targets."

## v3.47 (MR-032)

Book List rebuild — replaces the tracker-based Monthly Mode (v3.44-46) entirely. The wishlist (renamed "Book List" in the UI; internal names/functions unchanged for lower risk) is now the single place both unread books AND reading progress live, with two live queues — Books and Audiobooks — computed fresh on every render rather than a one-time "consumed into a tracker" migration. - Book List items gained dateAdded, readingEntries ({id,date,pageTo}, same shape as a tracker's entries but scoped to just this one item — no bookId filtering needed), and completedDate. Backfilled once via backfillBookListFields(), set at creation everywhere a new item gets pushed (addToWishlistFromView, CSV import, deleteTracker's archive-back-to-wishlist, this file's own merge below). - bookListQueue(type) is the live "read order": every not-done item of that type, sorted per appState.monthlyConfig's bookSort/audioSort — dateAdded, tag (falls back to genre — matters for books merged in below, which predate tags being carried across), or manual (no sort at all: just the wishlist array's own stored order, which reorderWishlist already edits in place — "manual" needed zero new reorder code). - mergeMonthlyTrackerIntoBookList() is the one-time migration for anyone (Pete) who already had a v3.44-46 tracker-based "Monthly Reads" tracker: moves its books + reading history into the Book List as ordinary items, tombstones the tracker. Shown via a dashboard banner until run; safe to leave sitting unmerged. - Targets live in appState.monthlyConfig (per-type book count target, optional page/chapter target, sort mode, plus reading-goal collections) — a genuinely new, LOCAL-ONLY piece of state, unlike trackers/books/entries/wishlist which sync via pal-sync's four tables. Now included in buildJSON()'s export and doRestore()'s import, which previously only knew about trackers/wishlist — otherwise every JSON backup would have silently dropped it. - Active/Past is a screen-level split on the Book List, driven by completedDate specifically (not the done-for-queue-purposes check) so unfinishBookListItem can reopen a finished item for review without that undo silently un-completing it for Monthly-queue purposes too — those stay two different questions. - Reading-goal collections (name + target date + a chosen subset of books) are a read-only progress rollup over whichever books are picked — no separate logging plumbing; logging still happens through the Book List / Monthly widgets same as any other item. - Monthly reading history (monthlyStatsFor, renderMonthlyStatsSection) is new in the Stats tab: books finished and pages/chapters read per calendar month, with best-month highlights (by book count, and separately by pages — chapters aren't folded into "pages", wrong unit). Found while wiring this in: renderStats() (the existing period-tab stats) only ever read tracker entries — Book List reading would have been completely invisible to Last 7 days/This month/Year to date/All time. Fixed by adding a second aggregation pass over wishlist readingEntries alongside the existing tracker one.

## v3.32 (MR-017, HZN-004)

percent-based logging + a third tracking mode. Note: HZN-004 carries Horizon's issue prefix but its content (page targets, reading pace) is unambiguously this app — treated as a misfiled ticket ID, not a wrong-app request; worth correcting in Test & Issues. - MR-017: books can now be logged by % read instead of an absolute page number (book.logMode, per-book and persisted — a Kindle book stays in % mode across every future log). Percent is converted to an equivalent page number right at the input boundary (logFromBook/logFromNowReading); logPages() itself and everything downstream is completely unchanged, per the brief's "not a full rewrite" instruction. Toggle available on both the Now Reading card and each book's own log section. - HZN-004: a third tracker mode alongside the existing "no target" and "date-driven" — trackingMode 'pace': state an expected pages/chapters-per-day rate, and the app locks an "original" projected finish date from today's remaining pages (per the brief: "at start note the original date calculated"). That original is NEVER recalculated by ordinary page-logging — only an explicit pace change re-locks it, exactly like setting it fresh. Alongside it, a live "currently tracking to finish" projection uses ACTUAL average pace so far, with a days-ahead/behind delta against the locked original. Mode-switching is non-destructive (switching away from date/pace doesn't clear those fields, so switching back restores them). trackingModeOf() resolves the effective mode with full backward compatibility — existing trackers with no explicit trackingMode infer it from whether targetDate is set, unchanged from before this feature existed. - Scoping decision: pace mode gets its own display in Settings, the header subtitle, and the dashboard tracker card — it does NOT hook into the Now Reading widget's daily-requirement bar, which remains a "date mode" concept only. Pace mode's whole premise (projecting forward from actual pace) doesn't map onto "pages required today to hit a fixed deadline" the same way, and wiring a second bar variant into that widget was judged out of scope for this pass — flagged as a reasonable follow-up if wanted. - Found while building this: trackers have the exact same cross-device sync gap as MR-016's books/wishlist finding — pal-sync.js's pull() never pushes an update to a tracker that already exists in the cloud. Added pushTrackerNow(), wired into name/target-date/active-flag edits (pre-existing) and the new pace-mode setters, plus extended flattenForSync()'s tracker field whitelist to include the new pace fields so a brand-new pace tracker doesn't lose them on its first (local-only) push.

## v3.30 (MR-016)

the actual, confirmed root cause — found by reading the real pal-sync.js source Pete shared, not by guessing further. - Bug in v3.29's OWN diagnostics: "0 wishlist rows seen in cloud fetch" was checking row.id, but rows returned by fetchTableRows() are shaped { record_key, data, updated_at } — there is no row.id. Every prior diagnostic reading was meaningless; fixed to read record_key (prefix match) and row.data (tags/ownership) correctly, and now logs the CLOUD's own tagged/owned counts directly, independent of the merge outcome, so a genuinely empty/untagged cloud can be told apart from a merge that just didn't pick the tags up. - The real bug: table().pull() only ever pushes a record to Supabase if its id is brand-new (missing from cloud entirely) or an unconfirmed tombstone. There is no case in that function for "this id already exists in the cloud, my local copy is just newer, push it." That's a structural property of the shared library — confirmed from its source, not inferred — and it means the ordinary batched sync (pushAllToCloud → pullAllFromCloud → table().pull()) can never propagate an EDIT to a book or wishlist item that was already synced before the edit. Since virtually every one of Pete's 16 wishlist items and existing tracker books predate the tags/ownership/notes features, ordinary edits to them were silently never reaching the cloud via the normal sync path — regardless of how correct touch(), save(), or renderAll() were, because none of that matters if nothing ever calls upsert() for an existing record. - v3.29 already added pushWishlistItemNow() for wishlist edits, which sidesteps this correctly (upsert() is a plain PATCH-or-POST that doesn't care whether the record is new). This release extends the exact same direct-push pattern to books: pushBookNow(), wired into every book mutation (ownership, manual-complete, rating, review, notes, book edit, and the completedDate stamp in logPages) — correctly including trackerId, which flattenForSync()/reassembleFromSync() need to attach a pulled book to the right tracker. - No new Supabase table needed — this closes the gap without any infrastructure change, by no longer depending on table().pull()'s push step for anything except brand-new records and deletions, which is genuinely all it was ever designed to handle.
